## 星鼎 One 框架复用评估（2026-10-12）

对照 `~/projects/xingding-one-cli/template` 的 `platform/server`、`platform/identity`、`platform/authorization`、`platform/schema`、`adapters/production.go` 和 `web` 后，采用**按边界移植，不整体套用模板**。星鼎 One 是生成完整应用的内部 CLI，`./xdo create` 并非给已有项目加一个 Go 库；其生产装配仍显式连接 Demo 业务模块。元朴已经有 Electron/Vite 前端、TS Agent、OpenAPI/SDK 和迁移历史，整套生成会出现两个 Web Shell、两套账号/API 与两条迁移线。这里复用框架组织方式和 chi 依赖，不复制模板源码，也不把 Demo 身份、内存状态或签名密钥当作生产能力。

| 星鼎 One 的做法 | 元朴采用方式 | 当前状态 |
| --- | --- | --- |
| `platform/server` 用 chi 装配独立路由、统一请求元数据和健康接口 | Go HTTP Host 保留公开/健康路由；模块挂载路由，`httpkit` 统一请求 ID、JSON 限额、Bearer 解析和错误格式 | 已完成基础层；组件生命周期和资源预算未移植 |
| `adapters` 是进程装配点，Kernel 不导入业务 Module | `internal/app` 静态装配身份与内容模块；`cmd` 只管配置、命令和进程生命周期；Host 不导入业务包 | 已完成基础层，并有 import 边界检查 |
| 身份、授权、审计分离；授权基于服务端资源事实 | 保留当前账号表与会话兼容性，内容模块经 `internal/authorization` 检查当前用户/资源事实；搜索候选再过一次授权 | 已完成内容初版；附件、下载和能力执行尚不存在，身份管理仍是模块内规则 |
| Schema owner、校验和、只读启动探针和显式迁移 | 保留当前迁移序列及数据；新增领域迁移归属元数据和兼容检查时再逐步引入，不复制旧表 | 校验和与显式迁移已有；领域 ownership 未完成 |
| Web Shell、静态 catalog 和 Module UI | 浏览器门户单独建在本仓并复用设计原则；桌面 App 继续通过 TS SDK 接中心 | 未完成；不直接复制星鼎 One 的 Web Shell |

本轮明确不移植星鼎 One 的动态 Module/Plugin Runtime、命令/事件总线、Redis、MCP Host、生产 Demo 装配及 Web Shell：元朴首期只有静态内置模块，暂无需热装卸的服务端插件，也已有桌面 Web 与 TS Agent。后台 Worker 与可选计算服务进入开发时，再按实际故障隔离需求引入组件生命周期和资源预算。

下一步接浏览器门户与桌面客户端，并把附件/下载/能力执行纳入同一授权与审计链。Schema owner、备份恢复、会话治理与生产入口继续推进。所有复用以元朴自己的权限和业务验收为准，不能仅凭模板门禁宣称满足原规划。

## 元朴中心 Web 门户方向（2026-10-12）

用户明确元朴中心应是可独立在浏览器访问的 Web 服务网站，承载资讯、共享 AI 能力和组织知识；桌面侧栏的“元朴中心”只是连接它的客户端入口。当前独立 Web 前端与 Go API 分开开发，桌面内嵌中心网站，Electron 主进程只处理设备 Key 的安全保存和短期会话注入；网站从同域调用 Go API。部署时可由中心服务托管网站构建产物或使用同域反向代理；不另起一个服务端项目，也不将 Electron 页面直接当作网站。

参考站点与可借鉴的部分：

| 站点 | 借鉴点 | 元朴中心的对应设计 |
| --- | --- | --- |
| [SharePoint home site](https://learn.microsoft.com/en-us/sharepoint/home-site) 与[组织资讯示例](https://learn.microsoft.com/en-us/sharepoint/guided-walkthrough-set-up-news-with-hub-site) | 统一入口、全站导航/搜索、重点资讯与部门资讯的层级、内容审批 | 首页突出正式公告与精选资讯，完整资讯列表按分类和发布时间浏览；发布后的内容再进入首页 |
| [Hugging Face Spaces](https://huggingface.co/spaces) | AI 应用目录、按任务分类、搜索/筛选、作者和运行状态 | “AI 能力”以任务而非模型名组织；能力卡显示用途、提供者、可用状态、适用范围和入口 |
| [Poe Explore](https://poe.com/explore) | 清晰的搜索框和少量任务分类，官方能力有可辨识标记 | 首屏先给常用分类与精选能力，避免把完整目录一次堆到首页 |
| [GPT 分享与发布说明](https://help.openai.com/en/articles/8798878-sharing-and-publishing-gpts) | 能力详情包含描述、类别、能力与创建者信息；分享受权限和工作区策略约束 | 能力详情需说明输入/输出、示例、版本、归属、可用权限；发布与授权由中心控制 |

建议的站点导航为“首页 / 资讯 / AI 能力 / Wiki”，登录后再出现“我的工作台”；管理与审核入口由权限决定。首页采用网站式信息层级：品牌与全站搜索 → 一条重点资讯或公告 → 最近资讯 → 精选 AI 能力 → 推荐 Wiki。资讯可区分中心公告、产品更新、行业动态；AI 能力可按文档、检索、语音、研究等任务筛选。Wiki 是内容版块之一，不再占满中心首页。

网站可以先用明确标记的公开示例验证布局和路由，但这仅是开发预览，不是企业共享平台的交付。正式首版必须由中心真实存储资讯、Wiki 和 AI 能力目录，并让已登录成员完成提交、审核、发布、发现和使用的闭环。能力入口按实际执行位置区分：现有本地 Agent 能力显示“在客户端使用”，确有服务端 Worker 和授权接口的能力才显示“在线使用”；尚在开发的标明“规划中”，不放无效的执行按钮。桌面客户端可展示中心摘要并跳转或调用获授权的能力，但本机个人“知识库”仍是独立的数据空间。

### 企业内部分享的首版闭环

首版以单个组织为边界，由管理员创建或停用成员账号并配置团队；不开放匿名注册。成员可以撰写资讯、Wiki 词条和 AI 能力说明。每份资源都有创建者、归属团队、可见范围、版本和状态；首版可见范围先支持“本人草稿 / 指定团队 / 全组织”，项目级范围随项目模块实施。角色按原规划区分管理员、审核组、团队负责人、成员；团队负责人只审核本团队资源。能否读取、编辑、审核、发布、使用和撤回，由服务端按资源和动作判定。

内容状态为“草稿 → 待审核 → 已发布”，审核人可以退回，已发布版本可以撤回。修改已发布内容时生成新待审版本，旧版继续服务直到新版通过；撤回和权限变更后，列表、搜索、详情、附件、能力包下载及执行入口都应同步失效。首页只聚合当前成员有权读取的已发布内容，正式公告应与普通成员投稿可辨识。审核和发布记录保留操作者、时间、版本及结果。[SharePoint 的组织资讯与审批示例](https://learn.microsoft.com/en-us/sharepoint/guided-walkthrough-set-up-news-with-hub-site)提供了对应的分层发布参考。

AI 能力不是只有一张宣传卡。发布记录需写明用途、输入和输出、适用范围、维护者、版本、执行位置、所需权限和验证状态；有权成员能打开详情并经真实入口使用。可复用 Skill 或工具包走签名、版本和授权分发；服务端运行的能力由独立 Worker 执行，不能把现有本地 Agent 的工具调用伪装成网页端已可运行。共享级别与使用权限应分别表达，[受管理工作区的分享方式](https://help.openai.com/en/articles/8798878-sharing-and-publishing-gpts)可作交互参考。

真实首版的验收场景：管理员创建三名成员及审核人；成员 A 提交一篇资讯、一条 Wiki 和一项可在客户端使用的 AI 能力；审核人发布给指定团队；同团队成员 B 在网站搜索、阅读并通过客户端成功使用能力；其他团队成员 C 在首页、搜索、详情、下载和调用接口均无法取得这些资源；撤回后 B 也不再取得该版本。验收使用实际数据库和 API，重启服务后状态仍在。公开示例 API 只能作为开发联调材料，不能代替这条验收链路。

实现顺序据此调整为：先完成账号、团队、会话和资源授权；再做统一的资源版本、审核与发布契约及资讯/Wiki/能力目录的持久化；随后接入浏览器站点的阅读、投稿、审核和搜索，以及桌面客户端的授权使用；最后验证撤回、审计、备份恢复和跨团队拒绝。浏览器站点需要 HTTPS、会话保护和服务端授权，UI 隐藏按钮本身不构成权限控制。

检索依据：ZG 以“元朴中心 / Wiki / server-client / 门户”检索，命中本文件、`apps/app/src/modules/server-center.tsx` 与 `server/backend/internal/httpapi/wiki_preview.go`，结果 freshness 为 fresh；随后精确核对 Go 路由与客户端界面。外部参考使用上述站点及官方文档。

进入业务阶段前，本地 Agent 先完成 [Pi 1.0 npm 与内置 MCP 迁移](pi-1-migration.md)；该调整不改变 Go 中心及生成 TS SDK 的边界。

需求来源：用户提供的《20261010 下一步规划(1).md》，涉及 T1 账号权限、T2 经验积累与提取、T3 中心部署、T4 界面协作、T5 模拟法庭与语音转写。当前范围是全所推广，客户试用另阶段处理。

## 已确认的方向

- 保留在 yuanpu-agent 当前 Git 仓库，将 Go module 放在 `server/backend/`，独立网站放在 `server/web/`，形成可分别构建、部署和发布的中心服务。
- 技能目录和能力包分发已迁入 Go 的 catalog 模块；桌面与网站共用 `/v1/catalog` 接口。
- 桌面端、本地 Runtime、Listener/Worker 与 Agent 工具执行继续复用现有 TypeScript 实现。
- 中心采用 PostgreSQL；向量检索采用 pgvector；文件正文放文件存储。
- 模型评估、文档解析、中文转写等计算任务按需接独立 Worker 或模型服务。
- 先形成按业务模块组织的单体服务；需要进程隔离的计算 Worker 单独部署。

同仓有利于客户端、服务端、协议和权限行为一起修改与联调。独立部署不要求拆分仓库；以后有独立团队、代码访问权限或交付边界时再评估拆仓。

选择 Go 的依据是中心服务的部署、并发任务与长期维护方式。目前没有负载数据证明 Node.js 无法满足需求；更换语言也不会直接缩短模型调用或数据库等待。保留 TS Agent 实现，可以避免重写现有模型适配、工具与进程治理能力。

## 当前实现与变化范围

[Go 技能目录](../../server/backend/internal/catalog/http.go) 提供静态目录搜索、详情和受限能力包下载。Go 中心另有身份和内容接口；网站已能浏览公开目录，登录后可阅读有权访问的已发布资源，投稿、审核与管理页面仍需开发。

[Runtime 的包管理器](../../packages/yuanpu-runtime/src/packages/index.ts) 已通过 HTTP 消费目录接口。迁移需要保留既有目录契约，并为私有资源补齐客户端认证与服务端授权。

需求中“已有 SQLite 轻量鉴权”的表述，不能作为当前中心的实现基线；账号体系以 Go 后端源码为准。

本方案扩展了 [总体架构](../application-architecture.md) 和 [技能目录说明](../skill-catalog-server.md) 中“server 仅承担技能市场”的旧边界。实施时同步更新这些说明。本地 Agent 随 App 启停的生命周期不因中心上线而改变；中心与可选后台 Worker 则独立运行。

T3.1 的“中心只存、只发知识”与 T2.12 的“Server 评估优化”统一为：中心负责知识治理、数据与任务调度，计算交给可选 Worker；用户的本地操作任务仍由桌面 Agent 执行。计算 Worker 与需求中的任务 Worker Agent 是不同职责。

“四库”首先是四类业务数据，不等于四种数据库：

- Skill、Wiki、审核、版本、角色、项目与任务状态进入 PostgreSQL。
- 操作记录使用结构化事件，关联用户、项目、任务与产物；大文件和附件正文放文件存储。
- 文档分片、向量及其来源版本进入 PostgreSQL/pgvector。
- 人员关系、Wiki 链接与卡片分支先使用节点、边表实现。

T2.13 的本地习惯 Wiki 与可提交审核的个人经验词条要明确区分。日志回传采用明确字段范围，个人凭据与本地习惯信息不能因记录上传而进入中心。

## 技术选型

| 部分 | 首期选择 | 实施约束 |
| --- | --- | --- |
| API | Go + `net/http`、chi 路由 | 按业务模块注册，独立构建与发布 |
| 数据库访问 | PostgreSQL + pgx；按需配 sqlc | SQL、事务与数据库迁移保持显式 |
| 检索 | pgvector + 关键词/结构化条件 + 链接遍历 | 中文、案号、法条及权限过滤的召回效果需实测 |
| 权限 | 服务端角色与资源范围校验 | 结合团队、项目成员、归属与动作；不能只比较角色等级 |
| 文件存储 | 本地或 NAS 挂载目录 | 预留 S3 存储接口，文件访问经过授权 |
| 后台任务 | PostgreSQL 持久任务表 + Go Worker | 包含领取租约、重试、幂等、取消、失败与恢复状态 |
| Agent | 现有 TS Runtime/Assistant | 复用模型与工具能力，保持进程和权限隔离 |
| 专项计算 | 按需接 Python Worker 或模型服务 | 不把模型运行环境作为最小中心服务的强制依赖 |
| 接口契约 | OpenAPI + 生成 TS SDK | 不手工维护两份 Go/TS 接口定义；明确版本兼容策略 |
| 部署 | Docker Compose | Go 服务、PostgreSQL/pgvector、持久文件卷；计算 Worker 可选 |

先不引入 Redis、Kafka、独立向量数据库或图数据库；出现明确容量、延迟或运维瓶颈后再评估。具体版本在实施时选择受支持版本并固定。

PostgreSQL 的任务表可使用 `FOR UPDATE SKIP LOCKED` 支持并发领取，但完整任务语义仍需实现。pgvector 的近似检索与权限过滤组合可能影响召回数量，必须用真实授权范围验证，不能只测无过滤查询。

```text

├── apps/                         # 桌面端和本地 Runtime
├── packages/
│   └── yuanpu-server-client/     # 中心 API 的 TS SDK

    │   ├── go.mod
    │   ├── cmd/yuanpu-server/
    │   ├── internal/
```
