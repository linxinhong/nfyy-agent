## 已确认的方向

- 保留在 yuanpu-agent 当前 Git 仓库，在根目录 `server/` 建立独立 Go module，形成可独立构建、部署和发布的中心服务。
- 现有 Node 技能目录服务逐步迁入 Go 的 catalog 模块，迁移期间保留兼容验证路径，验收后替换。
- 桌面端、本地 Runtime、Listener/Worker 与 Agent 工具执行继续复用现有 TypeScript 实现。
- 中心采用 PostgreSQL；向量检索采用 pgvector；文件正文放文件存储。
- 模型评估、文档解析、中文转写等计算任务按需接独立 Worker 或模型服务。
- 先形成按业务模块组织的单体服务；需要进程隔离的计算 Worker 单独部署。

同仓有利于客户端、服务端、协议和权限行为一起修改与联调。独立部署不要求拆分仓库；以后有独立团队、代码访问权限或交付边界时再评估拆仓。

选择 Go 的依据是中心服务的部署、并发任务与长期维护方式。目前没有负载数据证明 Node.js 无法满足需求；更换语言也不会直接缩短模型调用或数据库等待。保留 TS Agent 实现，可以避免重写现有模型适配、工具与进程治理能力。

## 当前实现与变化范围

当前 [server 入口](../../server/src/index.ts) 提供技能搜索、详情与能力包下载，[目录数据](../../server/src/catalog.ts) 主要来自静态数组。它还不具备本需求描述的组织账号、权限、Wiki 审核与持久化。

[Runtime 的包管理器](../../packages/yuanpu-runtime/src/packages/index.ts) 已通过 HTTP 消费目录接口。迁移需要保留既有目录契约，并为私有资源补齐客户端认证与服务端授权。

需求中“已有 SQLite 轻量鉴权”的表述，不能作为当前 `server/` 的实现基线；账号体系需要按源码实际情况建设。

本方案扩展了 [总体架构](../application-architecture.md) 和 [技能目录说明](../skill-catalog-server.md) 中“server 仅承担技能市场”的旧边界。实施时同步更新这些说明。本地 Agent 随 App 启停的生命周期不因中心上线而改变；中心与可选后台 Worker 则独立运行。

## 服务与数据边界

| 归属 | 负责的能力 | 主要需求 |
| --- | --- | --- |
| Go 中心 | 账号、团队、权限、知识版本、审核、发布、检索、项目元数据、文件访问、日志接收、持久任务调度 | T1、T2.1—T2.6、T2.8、T3、T4.2 |
| 本地 TS Agent | 意图理解、Context 组装、Listener/Worker、子 Agent、工具调用、结果呈现 | T2.7、T2.8、T4.1、T5.1 |
| 可选计算 Worker | 评估、自审、索引构建、文档解析、转写及模型推理；向中心提交结果 | T2.5、T2.12、T5.2 |
| 本地个人存储 | T2.13 的习惯 Wiki、常驻层预算、个人凭据、脱敏映射 | T2.10、T2.13 |
| 桌面与管理界面 | 账号管理、审核队列、Wiki、卡片网络、项目看板、脱敏键值表 | T1、T2.6、T2.10、T4 |

T3.1 的“中心只存、只发知识”与 T2.12 的“Server 评估优化”统一为：中心负责知识治理、数据与任务调度，计算交给可选 Worker；用户的本地操作任务仍由桌面 Agent 执行。计算 Worker 与需求中的任务 Worker Agent 是不同职责。

“四库”首先是四类业务数据，不等于四种数据库：

- Skill、Wiki、审核、版本、角色、项目与任务状态进入 PostgreSQL。
- 操作记录使用结构化事件，关联用户、项目、任务与产物；大文件和附件正文放文件存储。
- 文档分片、向量及其来源版本进入 PostgreSQL/pgvector。
- 人员关系、Wiki 链接与卡片分支先使用节点、边表实现。

T2.13 的本地习惯 Wiki 与可提交审核的个人经验词条要明确区分。日志回传采用明确字段范围，个人凭据与本地习惯信息不能因记录上传而进入中心。

## 技术选型

| 部分 | 首期选择 | 实施约束 |
| --- | --- | --- |
| API | Go + `net/http` | 按业务模块组织，独立构建与发布 |
| 数据库访问 | PostgreSQL + pgx；按需配 sqlc | SQL、事务与数据库迁移保持显式 |
| 检索 | pgvector + 关键词/结构化条件 + 链接遍历 | 中文、案号、法条及权限过滤的召回效果需实测 |
| 权限 | 服务端角色与资源范围校验 | 结合团队、项目成员、归属与动作；不能只比较角色等级 |
| 文件存储 | 本地或 NAS 挂载目录 | 预留 S3 存储接口，文件访问经过授权 |
| 后台任务 | PostgreSQL 持久任务表 + Go Worker | 包含领取租约、重试、幂等、取消、失败与恢复状态 |
| Agent | 现有 TS Runtime/Assistant | 复用模型与工具能力，保持进程和权限隔离 |
| 专项计算 | 按需接 Python Worker 或模型服务 | 不把模型运行环境作为最小中心服务的强制依赖 |
| 接口契约 | OpenAPI + 生成 TS SDK | 不手工维护两份 Go/TS 接口定义；明确版本兼容策略 |
| 部署 | Docker Compose | Go 服务、PostgreSQL/pgvector、持久文件卷；计算 Worker 可选 |

先不引入 Redis、Kafka、独立向量数据库或图数据库；出现明确容量、延迟或运维瓶颈后再评估。具体版本在实施时选择受支持版本并固定。

PostgreSQL 的任务表可使用 `FOR UPDATE SKIP LOCKED` 支持并发领取，但完整任务语义仍需实现。pgvector 的近似检索与权限过滤组合可能影响召回数量，必须用真实授权范围验证，不能只测无过滤查询。

```text

├── apps/                         # 桌面端和本地 Runtime
├── packages/
│   └── yuanpu-server-client/     # 中心 API 的 TS SDK
└── server/

    ├── internal/
    │   ├── identity/             # 账号、团队、权限

    └── deploy/
```

## 需求调整与待明确事项

### 账号与权限

- 管理员建号、不开放注册的体验可以保留；密码改为保存哈希，初始密码不使用姓名拼音。
- [ ] 明确初始凭据交付、管理员重置、会话撤销与离职停用流程，替代明文密码字典及长期展示密码的设计。
- [ ] 将角色、团队/项目范围、资源归属和可见/可用/可改动作落实为统一授权规则。
- [ ] 明确普通成员可读取哪些已发布组织 Wiki。原权限表的“成员只读个人 Wiki”与组织知识共享目标存在冲突。
- 搜索、摘要、向量片段、关系链接、附件与下载都执行权限校验，不能仅在打开原文时检查。

### 知识分发与执行

- T2.8 的客户端解密意味着明文已到达用户电脑；加密 JS 不能保证组织知识无法被提取。
- 知识采用结构化数据传输，配合认证、最小范围下发、限流和审计。可执行 Skill 使用单独的签名、扫描、授权与限权运行流程。
- [ ] 明确是否存在必须对终端用户保密的知识；如有，相应步骤需要服务端执行，并重新确认中心的执行范围。
- [ ] 定义知识撤回、权限变更后的客户端缓存处理，以及版本过期规则。

### 评分、审核与自动优化

- 等级、质量评分和授权范围分别建模。EXP 或 Meta 分数可以触发审核申请，不能直接扩大可见范围。
- [ ] 明确“机器自动晋升组织 Skill”与“组织知识需要人审”的发布规则，自动优化产物先形成可追溯版本。
- [ ] 固定评分输入、评估器与规则版本，保留依据、历史结果和回滚点。
- [ ] 明确评估任务的模型配置、预算、失败重试及报告可见范围。

### 项目同步与个人数据

- [ ] 明确项目文件的权威版本、按需下载、冲突处理、删除传播和成员退出后的访问规则。
- [ ] 固定日志回传字段与脱敏边界，避免本地习惯、凭据或脱敏映射随日志上传。
- [ ] 明确哪些操作与产物进入组织经验沉淀，保留来源和授权范围。

### 部署与可用性

- Go 可以提供单个 API 可执行文件，完整中心仍需要数据库与文件存储，不能将其描述为无依赖的单文件系统。
- [ ] 确认 PC 是否必须支持无 Docker 原生安装；如必须，增加独立的安装与升级方案。
- [ ] 明确 NAS 的 CPU 架构、Docker 支持与存储条件，验证相应部署产物。
- [ ] 定义中心停机或 PC 休眠时定时任务的补跑策略；没有在线宿主就不能保证周六凌晨准时执行。
- [ ] 验证数据库、文件与版本元数据的一致备份、恢复和升级失败回退。

## 选型参考

- [Node Worker threads](https://nodejs.org/api/worker_threads.html)：CPU 密集任务与异步 I/O 的边界。
- [Go 并发模型](https://go.dev/doc/faq#goroutines)、[Go 目标平台](https://go.dev/doc/install/source)：并发与构建部署能力。
- [pgx](https://github.com/jackc/pgx)、[sqlc](https://sqlc.dev/)：Go 数据库访问与 SQL 类型生成。
- [pgvector](https://github.com/pgvector/pgvector)：向量检索、过滤与召回限制。
- [PostgreSQL SELECT](https://www.postgresql.org/docs/current/sql-select.html)：`SKIP LOCKED` 的队列用途及限制。
